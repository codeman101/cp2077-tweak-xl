# TweakXL StatService and TweakDB raw bindings: Mac signatures and evidence (Cyberpunk 2077 2.3.1, Mac arm64 vs Windows x64)

Read-only analysis. Mac RVA = VA - 0x100000000. Win = Windows RVA. Every twin below was compared by disassembly (rx w / rx m) plus caller pairs and vtable slots where stated.

## 0. What the port must change or watch first (summary of sections 1 to 3)

1. **StatsDataSystem_GetStatRange changes shape on the Mac.** The Windows row `uint64_t* (*)(void* aSystem, uint64_t* aRange, uint32_t aStat)` is wrong: the Mac function is `(x0 = this, w1 = stat) -> two floats in s0:s1` (HFA, no hidden pointer). Declare `struct StatRange { float min; float max; }` (plain aggregate) and the Raw type `StatRange (*)(void*, uint32_t)`, and write the handler as `StatRange OnGetStatRange(void*, uint32_t)` returning `{min, max}` or `{0.0f, 0.0f}` (section 1.3 has the code). The other four StatsDataSystem rows (InitializeRecords, InitializeParams, GetStatFlags, CheckStatFlag) keep their Windows prototypes exactly; all five Mac addresses are correct function starts and correct twins.
2. **GetStatRange, GetStatFlags and CheckStatFlag are virtuals with no direct callers** (Mac slots 0x208 / 0x210 / 0x218 of vptr 0x7239C58; Windows 0x200 / 0x208 / 0x210). Mac CheckStatFlag has GetStatFlags inlined, so a GetStatFlags hook does not see CheckStatFlag calls (keep both hooks, as TweakXL does). The entries of GetStatRange (+0xC) and GetStatFlags (+4) start with `cmp w1,#0x6ac; b.hi`, a PC-relative branch inside the first 16 bytes: the hook engine must relocate it. InitializeRecords, InitializeParams and CheckStatFlag have ordinary prologues. The offsets 0x3A939A0, 0x3A9472C, 0x3A93EF0, 0x3A93E74 (and TweakDB's 0x35F1BAC, 0x2B7CC9C) must be on the RED4ext-macos hook allowlist.
3. **Order: InitializeRecords runs immediately before InitializeParams, in the same job body** (Mac 0x3A951C4 / Win 0x9B3BF4), on a game job thread. A HookAfter on InitializeRecords therefore runs before InitializeParams reads the records array, and InitializeParams picks up every appended record (and the two dummies). InitializeParams also runs alone later from the ReloadParams virtual (slot 0x188).
4. **Lock protocol (this+0xFC): the Mac game uses writer = 0x80, readers = low bits; the Windows SDK protocol (writer = 0xFF) is incompatible.** The sibling SDK's SharedSpinLock has the Mac protocol on Apple (commit b383b5c27); the upstream pin of `vendor/RED4ext.SDK` in the TweakXL tree does not. The default CMake build uses the sibling SDK, so `std::shared_lock<Red::SharedMutex>` in the three handlers is correct as written; never build TweakXL against the vendor copy (it would also corrupt the TweakDB mutexes that TweakXL locks exclusively).
5. **Struct facts all hold on the Mac**: records DynArray at 0xD8 (size at 0xE4), params DynArray at 0xE8 (size at 0xF4) with 12 byte {min,max,flags} elements, lock byte at 0xFC, `Stat_Record.enumValue` at +0xD8 (default Invalid), StatType::Count = 0x6AD, Invalid = 0x6AE, records.size == Count after InitializeRecords, CEnum names array at +0x28 and values array at +0x38 (size 0x68), and the SDK's `EnumDescriptor::AddOption` matches the game's own add-option (sections 2.1 to 2.6).
6. **The TweakDB raws are all correct as declared** (Init `void(void*,void*)`, LoadOptimized `void(TweakDB*, CString&)`, TryLoad `bool(void*, TweakDB*, CString&, void*)`, CreateRecord `void(TweakDB*, uint32_t, TweakDBID)`); CreateRecord takes `mutex01` itself, which TweakXL respects. The Derive row has no Mac row but a Mac body exists at 0x34535C0 and the existing C++ replacement is equivalent (section 3).
7. **One robustness note**: RegisterStats installs the three getter hooks from inside the HookAfter handler, on a job thread, while other threads can already call them; and `.OrThrow()` there would unwind through the job thread. Installing them at OnBootstrap (and using HookWrap to fall through to the original while no custom stat exists) removes both risks (section 1.6).


## Shared facts for the StatsDataSystem class

- Class game::StatsDataSystem (reflection `gameStatsDataSystem`, parent `gameIStatsDataSystem`, size 336 = 0x150). The Mac class factory allocates 0x150 (`mov w2,#0x150` at 0x3A95148) and the constructor stores up to +0x148 on both sides.
- Constructor: Mac 0x3A92358 (thunk 0x3A92498) = Win 0x14192A4 (thunk 0x141929C). It stores the vptr (**Mac 0x7239C58, Win 0x2CC6BC8**) and initialises, identically on both sides: `[+0x48]=0`, `[+0x50]=0`, `[+0x78]=-1`, DynArray at 0x88/0x98/0xB0/0xC0/0xD8/0xE8 (empty, size 0), `dword [+0xF8]=5`, `byte [+0xFC]=0` (the lock), `[+0x118]=0`, `byte [+0x120]=0`, a CString at 0x128, `byte [+0x148]=0`.
- Only one vtable references the three getters. Mac slot = Windows slot + 8 for every slot used here (Mac has one extra leading slot): GetStatRecordID Win 0x1F0 / Mac 0x1F8, GetStatRecord Win 0x1F8 / Mac 0x200, **GetStatRange Win 0x200 / Mac 0x208, GetStatFlags Win 0x208 / Mac 0x210, CheckStatFlag Win 0x210 / Mac 0x218**, ReloadParams Win 0x180 / Mac 0x188, job scheduler Win 0x1A0 / Mac 0x1A8. The three getters are three consecutive vtable entries on both sides (Mac data slots 0x7239E60, E68, E70; Win .rdata 0x2CC6DC8, DD0, DD8), in the order Range, Flags, Check.
- Stat enum numbers (proved in section 2): **StatType::Count = 0x6AD = 1709, Invalid = 0x6AE = 1710 on the Mac as well**. The valid index range of every original getter is stat < 0x6AD (Win `cmp r8d,0x6ad; jae`, Mac `cmp w1,#0x6ac; b.hi`).
- Lock byte at this+0xFC: described in section 2.3.

## 1. THE FIVE StatsDataSystem ROWS

### 1.1 StatsDataSystem_InitializeRecords   Mac 0x3A939A0   Win 0x60BA84   HIGH

- Plain function, not virtual (no data pointer to it on either side). **One direct caller on each side**, which is also the only caller of InitializeParams from the init path: Mac `bl 0x3A939A0` at 0x3A9532C inside 0x3A951C4; Win `call 0x60BA84` at 0x9B3CB2 inside 0x9B3BF4. Not inlined anywhere (the Mac body is a real 0x1A0 byte function, size 0x3A939A0..0x3A93B40).
- **Prototype, unchanged from Windows: `void (*)(void* aSystem)`.** Mac x0 = this (x19); Win rcx = this (rdi). No result, no further argument. The HookAfter callback `void OnInitializeStats(void*)` is exactly the Raw argument list, so the existing TweakXL declaration and handler compile and run unchanged.
- Body twin (both sides): fetch the CRTTI system and call its virtual at +0x18 (GetEnum, SDK `CRTTISystem::GetEnum` slot 0x18) with the CName 0x743066319F27468D (= FNV1a-64 of "gamedataStatType", verified) -> the StatType CEnum; reserve the array at **this+0xD8** to 0x6AD entries of 8 bytes (Mac: `if capacity([+0xE0]) <= 0x6AC: DynArray_Realloc(arr, 0x6AD, 8, 4, 0)` with 0x286E8; Win call 0xA11D64 with edx=0x6AD); then loop i = 0 .. 0x6AC (0x6AD iterations: Mac `cmp x22,#0x6ad; b.eq`, Win `mov ebx,0x6ad ... sub rbx,1; jne`): enum value -> name through the CEnum value list (Mac 0x21A37CC / Win 0x60C748, twin pair shown in section 2.4), build the string "BaseStats." + name (Mac string at 0x6D6CBFA, Win 0x2AFA6E0, 10 characters), turn it into a TweakDBID (Mac 0x3453738 / Win 0x60A8E0), and push it onto the array at 0xD8 (Mac inline grow x1.5 with DynArray_Realloc(...,8,4,0); Win call 0x11F400).
- Result: records[0..0x6AC] hold TweakDBID("BaseStats.<enumName>") for every real stat, **records.size == 0x6AD == StatType::Count at the HookAfter point** (the constructor leaves size 0 and this is the only code that fills the array; one caller, one run).
- Entry bytes: `sub sp,sp,#0xC0; stp x28,x27,[sp,#0x60]; stp x26,x25,[sp,#0x70]; stp x24,x23,[sp,#0x80]`. No PC-relative instruction in the first 16 bytes. **Safe for an entry hook.**
- Hook note: the row hashes in the resolver table (lib/Support/macOS/TweakXLAddressResolver.cpp) already carry this start address.

### 1.2 StatsDataSystem_InitializeParams   Mac 0x3A932A8   Win 0x1908C0   HIGH

- Plain function, not virtual. **Two direct callers on each side** (the Windows and Mac sets are twins):
  1. the init job body, directly after InitializeRecords: Mac 0x3A95334 in 0x3A951C4, Win 0x9B3CBA in 0x9B3BF4;
  2. the ReloadParams virtual: Mac 0x3A9328C in 0x3A93268 (vtable slot 0x188, data slot 0x7239DE0), Win 0x1CBA7E9 in 0x1CBA7C0 (slot 0x180, data slot 0x2CC6D48). That virtual takes the exclusive lock at this+0xFC (Mac `bl 0x20C0`, Win `call 0x2F0968`), sets params.size ([+0xF4] / Win [+0xF4]) to 0, calls InitializeParams, releases the lock (Mac `mov w8,#-0x80; ldclralb w8,w8,[x20]`, Win `xchg byte [rsi+0xFC],dil` with dil=0) and then tail-continues into 0x3A93778 / Win 0x1516768 (same tail on both sides). So InitializeParams can run again later without InitializeRecords; the records array (with the custom entries) simply persists.
- **Prototype, unchanged: `void (*)(void* aSystem)`** (Mac x0 = this, Win rcx = this, no result). TweakXL declares the Raw row but does not hook or call it.
- Body twin: reserve the array at **this+0xE8** to records.size (read from [this+0xE4]; element size 12, alignment 4: Mac `mov w2,#0xC; mov w3,#4; bl 0x286E8`, Win `lea r8d,[r9+8]` with r9d=4, call 0x14B9D0); for each TweakDBID in the records array at this+0xD8 (stride 8): get the record handle (Mac 0x265A890 with x8 = sret, x0 = id / Win 0x190FB8; an id with hash 0 or length 0 gives an empty handle: Mac `cmp w0,#0; ccmp x8,#0` / Win `test edx,edx; shr rax,0x20; test al,al`); defaults min = -FLT_MAX (0xFF7FFFFF), max = +FLT_MAX (0x7F7FFFFF), flags = 0; when the record exists, read two floats through the TweakDB flat getter (Mac 0x968B5C / Win 0x33F8BC) at **record+0xC0 (min) and record+0xCC (max)** and use them only when max > min (Mac `fcmp s8,s0; b.ge` skip / Win `comiss xmm0,[rdi]; jbe` skip); flags are the OR of 1 "Bool", 2 "EquipOnPlayer", 4 "EquipOnNPC", 8 "ExcludeRootCombination" (CNames 0xF7BDD5A7C820889D / 0x48D5891F46728837 / 0x4C698D8A0D4F5689 / 0xE39628BFB0D25AC4, FNV1a-64 verified) found in the CName array at record+0x90 (Mac 0x9B8EF8 / Win 0x33F164; Mac inlines the flag function Win 0x19102C); push {min, max, flags} onto the params array (Mac `stp s8,s9,[x8,#-0xC]; stur w23,[x8,#-4]`, Win 0x1909E8: `[+0]=min [+4]=max [+8]=flags`). At the end Mac and Win shrink the array to the exact size.
- Consequence for TweakXL: InitializeParams reads **records.size and the array contents at entry** (Mac `ldr w1,[x0,#0xE4]`, `ldr x22,[x20,#0xD8]`), so it sees every entry appended by a HookAfter on InitializeRecords, including the two dummy entries (invalid TweakDBID -> params {-FLT_MAX, +FLT_MAX, 0}) and the custom records (their min/max/flags are taken from the records' own flats at +0xC0/+0xCC/+0x90).
- Entry bytes: `sub sp,sp,#0x80; stp d9,d8,[sp,#0x10]; stp x28,x27,[sp,#0x20]; stp x26,x25,[sp,#0x30]`. Ordinary, no PC-relative instruction in the first 16 bytes. Safe for an entry hook.

### 1.3 StatsDataSystem_GetStatRange   Mac 0x3A9472C   Win 0x287B14   HIGH   (**signature CHANGES**)

- **A virtual, no direct callers on either side.** Mac vtable 0x7239C58 slot **0x208** (data slot 0x7239E60), Win vtable 0x2CC6BC8 slot **0x200** (data slot 0x2CC6DC8). No other data pointer to the function.
- **Windows:** `uint64_t* GetStatRange(this = rcx, out = rdx, stat = r8d)`: writes the 8 bytes {min, max} (`movsd xmm0,[rax+r8*4]` with r8 = 3*stat, so element stride 12, `movsd [rdi],xmm0`) to the hidden pointer and returns it in rax; out of range writes 0 (`mov [rdx],rax` with rax=0).
- **Mac:** `(this = x0, stat = w1) -> two floats in s0 (min) and s1 (max)`. The body starts `movi d1,#0; movi d0,#0; cmp w1,#0x6AC; b.hi ret` (so out of range returns {0.0f, 0.0f} in s0:s1), then takes the shared lock, `ldr x8,[x20,#0xE8]; umaddl x8,w19,w9(=12),x8; ldp s0,s1,[x8]`, releases the lock and returns. **There is no hidden pointer argument: the Windows `uint64_t* aRange` argument disappears and the result is a homogeneous float aggregate returned in s0:s1** (AAPCS64 HFA of two floats).
- Caller twin (proves the register roles and that s0 is the first float): Win 0x251F934 (size 0xA7) calls the stats-system accessor 0x287B84, `lea rdx,[rsp+0x50]` (out), `mov r8d,[rsp+0x58]` (stat), `call [rax+0x200]`, `movss xmm0,[rsp+0x50]; movss xmm1,[rsp+0x54]`, stores them at entry+0x14 and entry+0x18, then `mov r8d,1; mov edx,[rdi+0x10]; mov r9,[rcx+0x210]; call r9; mov [rdi+0x20],al` (= CheckStatFlag(stat, 1)). Mac 0x3AB9FE8 (size 0xA4) calls the accessor 0x3A7ED6C (Win 0x287B84 twin), `ldr w1,[sp,#0x1C]` (stat), `ldr x8,[x8,#0x208]; blr x8`, **`stp s0,s1,[x22,#0x14]`** (min at +0x14, max at +0x18), then `ldr w1,[x22,#0x10]; ldr x8,[x8,#0x218]; mov w2,#1; blr x8; strb w0,[x22,#0x20]`. Same entry layout (stat +0x10, min +0x14, max +0x18, flag +0x20) on both sides.
- Further Mac callers of slot 0x208 that obtain the stats system through the accessor 0x3A7ED6C (functions): 0x3A7C5CC, 0x3A7CBCC, 0x3A7D4BC, 0x3A7D8B8, 0x3A80130, 0x3A80384, 0x3A80734, 0x3A812D4, 0x3A815F8, 0x3AB9FE8, 0x3ABB320. All reach the function through the vtable, so an entry hook sees all of them. The body is not inlined into any caller (the lock at +0xFC is taken by exactly these three getters (shared) and the ReloadParams virtual (exclusive): I scanned all 2755 callers of the shared-lock function 0x2098 and all 5969 callers of 0x20C0 for an `add xN,xM,#0xFC` feeding the call).
- **What a C++ detour has to declare on the Mac:**
  ```cpp
  #if defined(__APPLE__)
  namespace Red { struct StatRange { float min; float max; }; }   // plain aggregate, no ctor, not packed: an HFA, returned in s0:s1
  namespace Raw::StatsDataSystem {
  constexpr auto GetStatRange = Core::RawFunc<Red::AddressLib::StatsDataSystem_GetStatRange,
      Red::StatRange (*)(void* aSystem, uint32_t aStat)>();
  }
  #endif
  // StatService.hpp, Apple branch (Hook<> needs the callback to be exactly OriginalFunc<Raw return, Raw args>):
  static Red::StatRange OnGetStatRange(void* aSystem, uint32_t aStat);
  // StatService.cpp, Apple branch:
  Red::StatRange App::StatService::OnGetStatRange(void* aSystem, uint32_t aStat)
  {
      if (aStat != InvalidStat) {
          auto& statParams = Raw::StatsDataSystem::StatParams::Ref(aSystem);
          auto& statLock = Raw::StatsDataSystem::StatLock::Ref(aSystem);
          std::shared_lock _(statLock);
          if (aStat < statParams.size) return {statParams[aStat].min, statParams[aStat].max};
      }
      return {0.0f, 0.0f};
  }
  ```
  A `uint64_t` return (the shape of the current Windows-shaped row `uint64_t* (*)(void*, uint64_t*, uint32_t)`) is wrong on Mac in two ways: the pointer argument would take x1 so `aStat` would be read from w2 (garbage), and a `uint64_t` result would travel in x0 while the game callers read s0:s1. `std::pair<float,float>` and anything with a user-provided copy constructor must not be used (non-trivial for calls, becomes indirect through x8).
- Entry bytes: `movi d1,#0; movi d0,#0; cmp w1,#0x6ac; b.hi 0x3A94784`. **A PC-relative conditional branch sits in the last slot of the first 16 bytes (+0xC)**, target 0x3A94784 is a `ret` inside the function. An entry hook that overwrites 16 bytes must relocate `b.hi` (Gum's arm64 relocator rewrites b.cond; a patch of 12 bytes or less avoids it). The function start is a real function start (LC_FUNCTION_STARTS).

### 1.4 StatsDataSystem_GetStatFlags   Mac 0x3A93EF0   Win 0x65524C   HIGH

- **A virtual.** Mac slot **0x210** (data slot 0x7239E68), Win slot **0x208** (data slot 0x2CC6DD0). No direct caller on the Mac. On Windows the only direct caller is CheckStatFlag (`call 0x65524C` at 0x655239); **on the Mac CheckStatFlag has this body inlined** (it loads `[x8,#8]` itself and never calls 0x3A93EF0), so a hook on GetStatFlags does not intercept CheckStatFlag on the Mac. On Windows the direct call from CheckStatFlag would reach a GetStatFlags hook anyway; on the Mac both functions must be hooked separately, which is what TweakXL does (keep both).
- **Prototype, unchanged: `uint32_t (*)(void* aSystem, uint32_t aStat)`**: Mac x0 = this, w1 = stat, result in w0; Win rcx, edx, eax. Out of range returns 0 (Mac `mov w0,#0; ret`, Win `xor eax,eax`).
- Body twin: `cmp w1,#0x6ac; b.hi` / Win `cmp edx,0x6ad; jae`; shared lock at +0xFC (Mac `add x21,x0,#0xFC; bl 0x2098`, Win `lea rbx,[rcx+0xFC]; call 0x2167F4`); `ldr x8,[x20,#0xE8]; umaddl x8,w19,w9(12),x8; ldr w0,[x8,#8]` / Win `mov eax,[rax+rdx*4+8]` with rdx = 3*stat; `ldaddalb -1` unlock / `lock xadd byte [rbx],cl` with cl=-1.
- Callers: no caller of slot 0x210 (Mac) that reaches the system through the accessor 0x3A7ED6C was found, and none of slot 0x208 on Windows through 0x287B84; the consumer that proves the argument and result roles is CheckStatFlag (Win: `mov ebx,r8d; call 0x65524C; test ebx,eax; setne al`). So the prototype is proven by the body twin plus that call pair; no external caller pair was located (state this as the limit of the evidence).
- Entry bytes: `cmp w1,#0x6ac; b.hi 0x3A93F44; stp x22,x21,[sp,#-0x30]!; stp x20,x19,[sp,#0x10]`. **PC-relative `b.hi` at +4**, target `mov w0,#0; ret` at 0x3A93F44 inside the function. Needs the same relocation as GetStatRange (or a patch of 4 bytes).

### 1.5 StatsDataSystem_CheckStatFlag   Mac 0x3A93E74   Win 0x655230   HIGH

- **A virtual.** Mac slot **0x218** (data slot 0x7239E70), Win slot **0x210** (data slot 0x2CC6DD8). No direct caller on either side.
- **Prototype, unchanged: `bool (*)(void* aSystem, uint32_t aStat, uint32_t aFlag)`**: Mac x0 = this, w1 = stat, w2 = flag (kept in x19, `tst w8,w19`), result `cset w0,ne` (0 or 1) in w0; Win rcx, edx, r8d, `setne al`. Out of range: Mac sets the flags value to 0 (`mov w8,#0; tst w8,w19; cset w0,ne`) so it returns false, Win calls GetStatFlags, which returns 0, so also false.
- Body twin: Windows is `GetStatFlags(this, stat) & flag != 0` (`mov ebx,r8d; call 0x65524C; test ebx,eax; setne al`); Mac is the same operation with GetStatFlags inlined (bounds check 0x6AC, shared lock, `ldr w8,[x8,#8]`, `ldaddalb -1`, `tst w8,w19; cset w0,ne`).
- Caller twin: the 0x251F934 / 0x3AB9FE8 pair of 1.3 (CheckStatFlag(stat, 1) stored as a byte at entry+0x20). Other Mac callers of slot 0x218 through the accessor: 0x3A7FFD4, 0x3A80A80 (3 calls), 0x3A85FEC (3), 0x3A86180 (3), 0x3AB9FE8, 0x3ABB320; all virtual.
- Entry bytes: `stp x22,x21,[sp,#-0x30]!; stp x20,x19,[sp,#0x10]; stp x29,x30,[sp,#0x20]; add x29,sp,#0x20`. Ordinary prologue, no PC-relative instruction in the first 16 bytes (the `cmp w1,#0x6ac; b.hi` comes after it). Safe for an entry hook.

### 1.6 Order during game start, and where the hooks run

- InitializeRecords and InitializeParams are called **back to back from one job body**, in this order: Mac 0x3A951C4 (`bl 0x3A939A0` at 0x3A9532C, `bl 0x3A932A8` at 0x3A95334) = Win 0x9B3BF4 (`call 0x60BA84` at 0x9B3CB2, `call 0x1908C0` at 0x9B3CBA, with `mov rcx,[rdi]` between). The body twin of the surrounding code: both first copy the entries (0x20 bytes each, count at [+0x4C], array at [+0x40]) of a table behind this+0x48 into the hash map at this+0x58, then the two calls, then the rest (Mac 0x3A93BD8 and others, finally `bl 0x3A93778` = Win `call 0x1516768`, the same function that ReloadParams tail-continues into).
- So **InitializeRecords strictly precedes InitializeParams, with no other work between them**; a HookAfter on InitializeRecords runs after the records array is complete and before InitializeParams reads it. This is the only point at which the records array is built; the later ReloadParams path calls InitializeParams alone.
- The job body is scheduled by a virtual of the same class: Mac slot 0x1A8 (fn 0x3A92614, data slot 0x7239E00) = Win slot 0x1A0 (fn 0xA9D144, data slot 0x2CC6D68). Both build a job queue (`mov w1,#2; mov x2,#0; bl 0x9D420C` / Win `mov dl,2; xor r8d,r8d; call 0x218B34`), load the address of the body (Mac `adrp/add 0x3A951C4` at 0x3A926B4, Win `lea rax,[0x15E9110]`, the lambda wrapper that calls 0x9B3BF4) and store the resulting job handle at this+0x118 (Mac `str x0,[x19,#0x118]`, Win `mov [rbx+0x118],rax`). **Consequence: the HookAfter handler runs on a game job thread, not the main thread**, and the TweakDB must already be loaded (the body calls GetRecord for every id; the Windows build has the same property).
- Practical notes for StatService: (1) the three getters are hooked lazily from inside the HookAfter handler (`Hook<...>(...).OrThrow()` in RegisterStats). Other game threads can call GetStatRange at that moment, so the Attach must be safe against concurrent callers (the RED4ext-macos Attach goes through Gum; the offsets 0x3A9472C, 0x3A93EF0 and 0x3A93E74 must be on its GUM_OFFSETS allowlist, as must 0x3A939A0 for the HookAfter itself). (2) An exception thrown by OrThrow inside the handler would unwind through a job thread: prefer installing the three getter hooks at OnBootstrap time (a hook that only matters once s_statTypesModified is set can test the flag inside the handler and fall through to the original).

## 2. THE STRUCTS BEHIND THEM (src/Red/StatsDataSystem.hpp, StatService.cpp)

### 2.1 StatsDataSystem members 0xD8 (records) and 0xE8 (params)   HIGH

- Both are `DynArray<T>` in the SDK layout (data +0, capacity +8, size +0xC; SDK DynArray.hpp 323-325, and the Mac game's DynArray_Realloc 0x286E8 reads capacity at +8 and stores `[arr]`, `[arr+8]`). **records = this+0xD8 (data 0xD8, capacity 0xE0, size 0xE4), element TweakDBID, 8 bytes; params = this+0xE8 (data 0xE8, capacity 0xF0, size 0xF4), element 12 bytes.**
- Mac evidence: the constructor 0x3A92358 initialises the two arrays and clears `str wzr,[x19,#0xE4]` / `str wzr,[x19,#0xF4]` (Win 0x14192A4 sets `[rcx+0xD8]`,`[rcx+0xE0]`=0 and `[rcx+0xE8]`,`[rcx+0xF0]`=0 with the same empty-array sentinel). InitializeRecords: capacity test `ldr w8,[x19,#0xE0]; cmp w8,#0x6AC`, data `ldr x27,[x19,#0xD8]`, size `str w26,[x19,#0xE4]` after each push. InitializeParams: `ldr w1,[x0,#0xE4]` (records size), `ldr w8,[x0,#0xF0]` (params capacity), `str w25,[x20,#0xF4]` (params size), `ldr x8,[x20,#0xE8]; umaddl x8,w25,w26(=12),x8` (params data). Windows: `mov edx,[rcx+0xE4]; lea rsi,[rcx+0xE8]; cmp [rsi+8],edx; mov rbx,[rdi+0xD8]; mov eax,[rdi+0xE4]` and `mov [rsi+0xC]` for the params size. Identical offsets on both sides. The capacity growth rule on both is 1.5x.
- The buffer layout of the game's arrays is `[capacity*elemSize rounded up to 8][allocator pointer]` (Mac 0x286E8: `add x11,x12,#7; and #-8`, allocator stored at the end), which is what the SDK's `DynArray::GetAllocator()` assumes, and the SDK reallocates through the same function (`SetCapacity` -> DynArray_Realloc, Mac row 0x286E8, args `(arr, newCap, sizeof(T), max(alignof(T),8), nullptr)`). The only difference from the game's own call is the allocation alignment argument (the game passes 4 for the records array, the SDK passes 8); the alignment is only given to the allocator, the layout is fixed, so `statRecords->EmplaceBack()` / `PushBack(recordID)` from the plugin are safe on the Mac.
- `Red::DynArray<Red::TweakDBID>` EmplaceBack() default-constructs a zero TweakDBID (hash 0, length 0): the dummy entries. InitializeParams treats such an id as "no record" and produces {-FLT_MAX, +FLT_MAX, 0} for it (1.2).

### 2.2 The params element (`Red::StatParams`)   HIGH

- Element = 12 bytes: **`float min` at +0, `float max` at +4, `uint32_t flags` at +8**, stride 12. Mac: `ldp s0,s1,[x8]` (GetStatRange), `ldr w0,[x8,#8]` (GetStatFlags), `umaddl ...,w9(=0xC),x8`; InitializeParams stores `stp s8,s9,[x8,#-0xC]; stur w23,[x8,#-4]` after incrementing the size. Windows: `movsd xmm0,[rax+r8*4]` with `lea r8,[rsi+rsi*2]` (12*stat), `mov eax,[rax+rdx*4+8]`, and 0x1909E8 `[rax]=min`, `[rax+4]=max`, `[rax+8]=flags`.
- TweakXL's `Red::StatParams { #pragma pack(1) union {uint64_t range; struct {float min; float max;};}; uint32_t flags; }` is 12 bytes on clang (union alignment 1, size 8, `flags` at offset 8, struct alignment 4), so `Red::DynArray<Red::StatParams>::operator[]` strides by 12. `range` (a uint64_t) is only meaningful on Windows; on the Mac use `min` and `max` (section 1.3).

### 2.3 The lock at this+0xFC   HIGH

- It is a **one-byte reader/writer spin lock** (constructor `strb wzr,[x19,#0xFC]` = Win `mov byte [rcx+0xFC],dl`), the same object kind as the TweakDB mutexes. The three getters hold it shared; the ReloadParams virtual holds it exclusive while it rebuilds the params array.
- **Mac protocol** (game functions 0x2098, 0x20C0, 0x20E8, 0x2100): shared lock = `ldaddalb +1` and, when the old value had bit 7 set, wait (`wfe`) until bit 7 clears; shared unlock = `ldaddalb -1`; exclusive lock = wait until the byte is 0, then `casalb 0 -> 0x80`; exclusive unlock = `ldclralb` with 0x80 (clears bit 7, keeps the reader count); try-exclusive = `casalb 0 -> 0x80`; try-shared = CAS +1 only while bit 7 is clear. So **a writer is 0x80, readers are the low 7 bits**.
- **Windows protocol** (0x2167F4, 0x2F0968): shared lock = `cmpxchg` byte -> byte+1 unless the byte is 0xFF; exclusive lock = `cmpxchg 0 -> 0xFF`; shared unlock = `lock xadd byte,-1`; exclusive unlock = `xchg byte,0`. A writer is 0xFF.
- The two protocols are not compatible: a Windows-style reader added to a Mac writer (0x80) is accepted (0x80 != 0xFF) while the game still writes, and a Windows-style writer (0xFF) is wrapped to 0 by a Mac reader's `+1` and then lets the reader through, after which the reader's `-1` can leave the byte at 0xFF (stuck writer).
- **What TweakXL has to use:** `std::shared_lock<Red::SharedMutex>` is `RED4ext::SharedMutex`, a deprecated alias of `RED4ext::SharedSpinLock` (SharedMutex.hpp). **The sibling SDK (`RED4ext.SDK-macos`, commit b383b5c27, "SharedSpinLock follows the Mac game's lock protocol on Apple (R21)") implements exactly the Mac protocol**: `TryLock` = CAS 0 -> 0x80, `Unlock` = `fetch_and(0x7F)`, `TryLockShared` = CAS +1 only while bit 7 is clear, `UnlockShared` = add -1. With that header, the existing `std::shared_lock _(statLock)` in OnGetStatRange / OnGetStatFlags / OnCheckStatFlag is correct on the Mac and needs no change (`Red::SharedMutex` is sizeof 1, `lock_shared`/`unlock_shared` exist). **The upstream pin of `vendor/RED4ext.SDK` in the TweakXL tree does NOT have the Apple branch** (verified: no `__APPLE__` in its SharedSpinLock-inl.hpp); `CMakeLists.txt` selects `../RED4ext.SDK-macos/include` by default on Apple (`TWEAKXL_SDK_INCLUDE`), so the default build is right, but a build with the vendor tree or an old `RED4EXT_SDK_DIR` would use the Windows protocol, which also breaks the `std::unique_lock<Red::SharedMutex>` writers TweakXL takes on `tweakDb->mutex00/mutex01` (Manager.cpp 111, 139, 172, 189, 394-413).
- A handler does not need its own lock type. The only requirement is that the plugin is compiled with the Apple SDK branch.

### 2.6 BaseStatCount, Count and Invalid   HIGH

- `Red::game::data::StatType::Count = 1709 = 0x6AD`, `Invalid = 1710 = 0x6AE` (SDK StatType.hpp, last real entry CPO_NPC_Importance = 1708). **The Mac enum has the same numbers**: the registration function 0x25EEF54 adds options by value (`mov w3,#0x6AB` for "CPO_Armor", `#0x6AC` "CPO_NPC_Importance", `#0x6AD` "Count" at 0x25FF250, `#0x6AE` "Invalid" at 0x25FF270, then registers the enum with `bl 0x2188408`), and the original code agrees: InitializeRecords loops 0..0x6AC (0x6AD entries), every getter allows stat < 0x6AD, and 0x3A93B4C defaults to 0x6AE.

- Not checked here: other game code that sizes per-entity arrays with the compile-time Count (the 84 `mov w,#0x6AE` sites on the Mac); a custom stat index >= 0x6AF is outside everything the original code was written for, on Windows as well.
